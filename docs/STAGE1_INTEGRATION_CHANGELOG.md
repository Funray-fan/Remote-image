# 第一阶段整合改动说明

记录日期：2026-11-11。对应本地分支 `feature/c1-stage1-integration`、提交 `a276b45`。本文供项目组审阅；上传和合并状态以 GitHub 实际分支及 Pull Request 为准。

## 一、整合范围与成果

本次以仓库 `main` 为基线，整合 C1、R2、R3、C2、C3 的阶段一成果，并选择性纳入 R1 的代码与数据清单。没有把原始影像、处理影像、模型权重、虚拟环境或运行产物纳入本次提交。

整合后可在本机启动 Streamlit 网页，选择涿州真实案例或合成功能样例，切换灾前、灾后、水体候选、建筑和道路图层，点击地图要素查看属性，查看统计、下载摘要，并从网页触发涿州案例重跑。真实案例的固定输入可由仓库中指定的 R1 Git 历史提交提取，脚本校验文件哈希；该取数方式仍依赖历史对象可用。

## 三、验收结论与限制

- 工程验收：本机 121 项测试通过；公共 schema 两份副本同步检查通过；真实与合成案例能在浏览器展示、查询和复跑。
- 涿州真实案例运行值：新增水体候选面积 9,683,100 m²，交叠建筑来源对象 8 个，交叠道路约 9,440.89 m。这些是当前输入与规则下的计算值，不是独立真值验证后的灾损结论。
- `pipeline_result.json` 保持 `partial`：人口输入、独立参考标签和实际建筑损毁模型尚缺；Precision、Recall、F1、IoU 不应填为已验证数值。道路与水体相交不能直接判定道路阻断。
- 当前涿州 SAR 洪水基线不接受普通 JPG/PNG 直接作为洪水分析输入；二阶段 xBD PNG 是建筑损毁模型的训练/推理输入，任务和输入规格不同。没有地理定位的 PNG 不能直接叠加到真实地图。

## 四、上传 GitHub 后别人能看到什么

仓库目前为公开仓库。把本分支推送并经 Pull Request 合并后，其他人可在 GitHub 查看源代码、配置、文档、测试、小型 fixture 与 `docs/acceptance/` 中的界面截图；克隆仓库后也可按 [本地运行说明](../本地运行说明.md) 配置并尝试复跑。

GitHub 仓库页面不会自动运行 Streamlit 网页，也不会自动展示本机 `outputs/` 中的动态结果。要让别人直接打开交互界面，需要另行部署；要让对方在其电脑复跑真实案例，还要确保固定输入数据可获取、许可可用，且安装所需依赖。截图可以展示界面，但不能替代真实运行记录和原始结果。

截至本文写作时，本整合分支仅在本地，GitHub 尚无同名分支。按仓库协作规则，应先推送功能分支、创建 Pull Request、完成下游岗位与 C1 审阅，再合并到 `main`；不要直接推送 `main`。本次新增提交未上传大型影像、模型权重或 `outputs/`。

## 五、对第二阶段计划的影响

**三阶段目标和岗位分工无需重排。** 第二阶段仍由 C2 负责 xBD 建筑灾损模型、评估、推理适配及模型清单；R1 按模型输入规格准备影像，R2 做空间和切片 QA，C1 接入工作流与校验，C3 在同一网页展示。需要把以下交接条件明确到开工和验收节点：

1. C2 先冻结版本化 `ModelInputSpec`：明确灾前/灾后波段顺序、颜色空间、尺寸、归一化、缺失输入处理及模型输出。R1 按此规格准备输入，不猜测训练预处理。
2. xBD 训练、验证和有标签测试按原始场景/影像对分组，检查空间重叠，记录类别分布与独立测试指标。C2 在外部设备训练后交付可加载权重或导出模型、依赖版本、模型清单、固定真实推理样例及期望输出；验收机只需安装推理所需环境，不必重训。
3. 阶段二出口必须有逐建筑 `damage_vector`、`tile_index`、元数据与模型版本，并记录 `building_id`、损毁等级、置信度和几何/ID 来源。不能把阶段一 C2 空基线当成真实模型，也不能仅以像素掩膜替代逐建筑结果。
4. xBD 与阶段一涿州案例若不是同事件、同覆盖范围且有可核验地理定位，应使用不同 `event_id` 分开展示和验收；不能把两套数据合并成一个真实灾区结果。后续要在同一事件联动洪水与建筑灾损，需另外取得适用的高分灾前/灾后影像并通过空间配准与模型适用性检查。
5. C1/C3 在现有网页新增阶段二结果入口和逐建筑查询；R2 对投影、覆盖范围、切片边缘与聚合结果做 QA。阶段二精度目标应在模型 baseline 和独立评估后由项目组确认，不能以阶段一工程测试通过代替效果验收。

上述是对原 v1.6 阶段二交接要求的具体落实，不改变第一阶段 SAR 洪水、第二阶段建筑损毁、第三阶段无人机核查与救援分析的主线。
